# War Library — Full Audit, 2026-07-25

Scope: whole repo at `db7f403` (master) plus live probes against
https://warlibrary.midatlantic.ai. Five parallel audit tracks — language/i18n,
UI/UX, API/security, pipeline, tests/CI/config/docs. Every finding below was
verified by reading the code or measuring the live site; nothing here is
inferred.

Context that reframes everything: **the live dataset is 24,632 events**, not the
3,800 the docs claim and not the "127+" the GitHub description claims. Most of
the severe findings below are the same root cause — the app was designed for
hundreds of events and is now running six-and-a-half times past even its own
stale documentation.

Prior audit `docs/AUDIT-2026-03-23.md` catalogued ~20 of the API-layer items.
Re-checked this pass: **none of them have been remediated.**

## P0 — Scale failures (the site is straining under its own data)

**P0-1 — `/api/events` ships the entire 24,632-event dataset on every load, then
again every 60 seconds.**
`src/hooks/useEvents.ts:32` fetches with `cache: "no-store"`;
`useEvents.ts:56-58` re-fetches on a 60 s interval. That is 4.5 MB gzip per
minute per open tab (~270 MB/hour), and 18 MB decompressed + parsed into JS heap
on the client each time. On a phone on cellular this is the difference between
a usable site and an unusable one. There is no pagination, no `?since=`, no
delta endpoint.
*Fix:* paginate/window the API (`?since=`, `?limit=`, `?bbox=`), have the poll
request only events newer than `last_updated`, and drop `no-store` so the
60 s `Cache-Control` actually does something.

**P0-2 — Every `GET /api/events` re-reads, re-parses, re-dedupes, re-sorts and
re-serializes all three data files synchronously.**
`src/app/api/events/route.ts:168-203` — three `fs.readFileSync` + `JSON.parse`
(`route.ts:63-73`), then `unique.sort()` allocating two `Date` objects per
comparison over 24 k items, then a full `.map(toSerializedEvent)`, then
`NextResponse.json` serializing 18 MB. All of it blocking, on the single PM2
Node process that also serves the site.
Measured: **~0.4 s of blocking compute per request** (0.80 s TTFB against a
0.42 s baseline). Benchmarked locally against the real dataset, the recompute is
~150 ms of CPU on a fast desktop; the droplet's 2 shared vCPUs account for the
rest. The problem is not the absolute number, it's that it is *synchronous and
per-request* — it caps the entire site at a couple of requests per second and
every other route queues behind it.
Note `src/lib/rag.ts:538-561` already implements exactly the right pattern —
a 30-second module-level cache of the same data. `/api/events` just doesn't use
it.
*Fix:* mtime-keyed module cache, `stale-while-revalidate`, ETag + 304 on the
poll path.

**P0-3 — The map renders up to 24,632 individual DOM markers, and re-renders all
of them on every pan/zoom frame.**
`src/components/map/ConflictMap.tsx:59-65` uses a controlled `viewState` with
`onMove={(evt) => setViewState(evt.viewState)}`, so every gesture frame is a
React re-render; `ConflictMap.tsx:137-168` maps every filtered event to a
`<Marker>` whose inline styles read `viewState.zoom`, so no marker can bail out
of rendering. No clustering, no cap.
*Fix:* GeoJSON `Source` + circle/symbol `Layer` with Mapbox native clustering
(`cluster: true`); at minimum switch to `initialViewState` + `onMoveEnd`.

**P0-4 — The event feed renders every event, unvirtualized, and re-filters +
re-sorts on every keystroke.**
`src/components/ui/EventPanel.tsx:38-55` runs `events.filter(...)` and
`[...filtered].sort(...)` inline in the component body — no `useMemo`, no
debounce — then `EventPanel.tsx:118-177` renders every row with nested
`ProvenanceRow`, `ShareButton`, SVGs. `src/app/page.tsx:308` passes the full
`events` array, not the map's `filteredEvents`, so the feed is never even
date-filtered.
*Fix:* `useMemo` the filter/sort, debounce search, virtualize the list, and sync
the feed to the timeline range.

**P0-5 — The admin dashboard blocks all public traffic.**
`src/app/api/admin/dashboard/route.ts:25-32, 69-118` runs six blocking
`execSync` calls — `pm2 jlist` (15 s timeout), `crontab -l`, `tail`,
`cat /proc/uptime`, `free -b`, `df -B1 /` — on the same single process serving
the site, and the admin UI polls it every 30 seconds. A slow `pm2 jlist` stalls
the entire site for up to 15 s. No injection risk today (hardcoded commands,
whitelisted cron intervals) but `runCommand` takes a shell string.
*Fix:* `execFile` with argv arrays, awaited async, short cache on the payload.

## P0 — Data quality (measured against the live 24,638-event dataset)

A snapshot of production was pulled locally and analysed. These are not code
smells — they are the actual contents of the live dataset, and several of them
are the predicted consequences of the pipeline bugs in the next section
occurring in the wild.

**P0-Q1 — 71% of the dataset is the catch-all bucket.**

| event_type | count |
|---|---|
| `strategic_development` | 17,547 |
| `airstrike` | 2,715 |
| `missile_attack` | 2,202 |
| `violence_against_civilians` | 882 |
| `drone_attack` | 881 |
| `battle` | 300 |
| `protest` | 121 |
| `explosion` | 102 |

A "war library" whose map is 71% non-kinetic "developments" is showing mostly
noise. This is also the bucket where dedup is weakest — `strategic_development`
events almost always carry `fatalities: 0`, and dedup methods 0 and 3 are both
fatality-gated, so they never fire on it.

**P0-Q2 — There is heavy residual duplication.** 566 distinct
`country + event_type + day` groups contain 10 or more events. The worst single
group is **125 Iran `strategic_development` events on 2026-04-13**; the top ten
groups all sit between 84 and 125. Given the pipeline extracts a maximum of ~20
articles per 30-minute run, ~125 distinct strategic developments in one country
in one day is not plausible — this is P0-7's blind spot (fatality-gated dedup)
made visible.

**P0-Q3 — The map is dominated by geocode-fallback piles.** Only **4,514
distinct coordinate pairs for 24,638 events**, and the reuse is extreme:

| coordinate | events | what it is |
|---|---|---|
| `32.4279, 53.688` | 4,908 | geographic centroid of Iran |
| `26.5667, 56.25` | 1,549 | Strait of Hormuz |
| `35.6892, 51.389` | 1,133 | Tehran |
| `26.5, 56` / `26.5, 56.5` | 503 / 464 | rounded Hormuz variants |

**One in five events in the entire dataset sits on Iran's centroid** — a single
marker pile in the middle of the country that represents 4,908 stacked events.
Plus **217 events at `0, 0`**, which render in the Gulf of Guinea off West
Africa, thousands of miles from any event in this conflict.

**P0-Q4 — `country` is unnormalised free text with 204 distinct values.** It
holds real countries alongside `"Multiple"` (500), `"Global"` (315),
`"International Waters"` (1,035), and 97 values that appear exactly once —
including `"Iran,Oman"`, `"Kuwait/Bahrain"` *and* `"Bahrain/Kuwait"` as separate
values, `"Pakistan,Turkey,Iran,United States"`,
`"Saudi Arabia, Qatar, Kuwait, Bahrain, Jordan, Germany, United Kingdom, Canada"`,
`"Multiple - Asia"`, and `"Cyprus/Gaza"`.
This means **every country count the site has ever published is unfounded** —
"17 countries", "28+ countries" and "60+ countries" are all just different
wrong readings of a field that cannot be counted as written. It also means the
map legend's country filter is unusable at the tail.
*Fix:* normalise to ISO 3166 codes at extraction time, with an explicit
multi-country array rather than a delimiter soup.

**P0-Q5 — Invalid and future dates are in production right now, exactly as
predicted.** 3 events have **unparseable dates**, and 2 events are dated
**2026-10-01 — over two months in the future**. Both future events are Gaza
cumulative casualty reports ("…kill 906 Palestinians and injure 2,747",
"1,168 Palestinians killed and 3,734 wounded"), i.e. they are simultaneously
(a) future-dated, (b) cumulative tolls the pipeline is explicitly supposed to
reject, and (c) invisible to every time-windowed dedup method. This is P1-Pipeline's
`NaN < CONFLICT_START === false` bug and the missing upper bound, both confirmed
live.

**P0-Q6 — Provenance gaps.** 243 events have no `source_url`, 244 have no
`confidence`, 148 have no `verification_status`. That is more than the 112 seed
events, so ~130 *pipeline-generated* events also lack the provenance the README
promises for every event.

**P0-Q7 — Fatality data is thin and the top of it looks like cumulative tolls.**
23,559 of 24,680 events carry `fatalities: 0`; total is 14,519 across the whole
dataset, concentrated in ~1,100 events. The largest single-event tolls include
entries that read as aggregates rather than events — "Hundreds of children
killed across the region according to U[N]" (340), "Israeli military reports
striking more than 1,100 Hezbollah [targets]" (350) — which is precisely what
the cumulative-toll rejection is meant to catch. Nothing sits at exactly 500,
confirming the `>= 500 → 0` zeroing rule has fired and erased whatever was there
without leaving a trace.

## P0 — Data integrity and deployment

**P0-6 — The pipeline marks articles "seen" *before* extraction, so any failure
loses those events permanently.**
`scripts/update-events.js:1272-1278` writes the article-URL cache immediately
after fetch. The Claude call (`:1436`), the JSON parse (`:1482-1560`) and the
file write (`:1809`) all happen after. An API error (`process.exit(1)` at
`:1447`), a parse failure (`:1559`), the 180 s timeout (`:1117`), or a crash
means the next run skips those articles forever (`:1282`). Same for every event
past the truncation point in a salvaged response.
*Fix:* write the cache only after events are successfully appended.

**P0-7 — Deduplication merges genuinely distinct events at country granularity.**
`scripts/update-events.js:904-917` (Method 0): same country + same
`event_type` + within 48 h + fatality ratio ≥ 0.7 ⇒ duplicate. There is **no
city, region, coordinate, or description check.** Two separate airstrikes on the
same day in Tehran and Isfahan (10 vs 12 dead, ratio 0.83) are declared the same
event, and the survivor's fatality count is then overwritten with the other's
(`:1700-1703`). Method 3 (`:919-931`, ±72 h, ratio ≥ 0.4) is worse: 85 dead and
180 dead in the same country within three days merge.
*Fix:* require haversine ≤ ~50 km or matching region, plus a minimum word
overlap, before either method fires.

**P0-8 — `deploy.sh` can wipe the 24,632-event production dataset.**
`deploy.sh:21` tars `.` excluding only `node_modules`, `.next`, `.env.local` —
so `src/data/*` and `.git` ship — and `deploy.sh:32` does a blind `tar xzf` over
`/opt/warlibrary`. Today's clone has no `events_latest.json`, so a deploy right
now is safe *by luck*. The moment you run the pipeline or the app locally, the
next deploy overwrites production's events, analytics, and notification state
with stale local copies. There is also no test/lint gate — only `npm run build`.
*Fix:* mirror the `.gitignore` runtime list into `--exclude` flags (or switch to
`rsync --exclude-from`), exclude `.git`, and run `npm test` before packaging.

**P0-9 — Write failures are swallowed and then reported as success.**
`scripts/update-events.js:703-716` — `writeJSON` catches and logs. If the
`events_latest.json` write at `:1809` fails (disk full), execution continues to
`STATUS: EVENTS_ADDED` (`:1822`), sends notifications, and — per P0-6 — the
articles are already cached, so the events are gone with a green status.
Related: the `typeof pipelineStats !== "undefined"` guard at `:712` is dead code
(`pipelineStats` is a `const` inside `main()`, invisible at module scope), so
write failures never reach stats either.

**P0-10 — A silently dying cron is never noticed.**
`main().catch` (`:1834-1837`) and the 180 s timeout handler (`:1114-1117`) both
exit without calling `writePipelineStats`, so `last_run` just goes stale with no
error recorded. The corruption guard (`:1169-1177`, exit 3) halts the pipeline
permanently and silently. `scripts/auto-update.sh` has no alert channel, and its
log at `/var/log/warlibrary-updates.log` has no logrotate config anywhere in the
repo (~0.5–1 MB/day, unbounded, on a 2 GB droplet).
*Fix:* write a failure stats record on both crash paths; add a dead-man's-switch
ping; ship an `/etc/logrotate.d/warlibrary`.

**P0-11 — Backups are same-disk, unchecked, and rotate away good copies.**
`scripts/backup-data.sh` has no `set -e` and prints "Backup complete" even if
`cp` failed; backups live on the same filesystem as the data; there is no
validity check before copying, so if `events_latest.json` corrupts, seven daily
runs rotate out every good backup within a week — precisely the window in which
P0-10's silent failure is running.

## P1 — Abuse, auth, and API robustness

**P1-1 — Rate limiting is bypassed by one header.**
`src/app/api/chat/route.ts:50-57` takes `cf-connecting-ip` or the **leftmost**
element of `x-forwarded-for`. Caddy appends to `X-Forwarded-For` and preserves
the client-supplied prefix, so the leftmost value is attacker-controlled;
`cf-connecting-ip` is only trustworthy for requests that actually came through
Cloudflare. The 10/hr chat cap is therefore advisory.
*Fix:* read the rightmost hop at the trust boundary (or have Caddy overwrite
`X-Real-IP` and read only that), and firewall the origin to Cloudflare ranges.

**P1-2 — The rate-limit map is never pruned.**
`chat/route.ts:15-18` — no cleanup interval, no `.delete()` anywhere in the file
(unlike `analytics/route.ts:43-48`, which does prune). Combined with P1-1, every
spoofed IP permanently allocates an entry on a 2 GB box.

**P1-3 — The "hard block abusers at 20" branch is unreachable.**
`chat/route.ts:34-46` — `entry.count` only increments on the *allowed* path, so
it saturates at 10 and `entry.blocked` is never set. The test at
`src/__tests__/api-chat.test.ts:396-417` fabricates `{count: 20}` to exercise it,
so the suite is green while the feature doesn't exist. The comment also calls it
a sliding window; it's a fixed window.

**P1-4 — The chat topic gate is effectively a no-op.**
`chat/route.ts:245` matches `CONFLICT_KEYWORDS` as bare substrings, and the list
includes `"us"`, `"air"`, `"who"`, `"what"`, `"how"`, `"oil"`. `"us"` matches
*just*, *must*, *because*, *focus*, *music*. Any natural-English prompt passes.
`BLOCKED_PATTERNS` (`:62-92`) are narrow literals — "compose a haiku" and
"disregard everything above" both sail through. The endpoint is usable as a
general-purpose Haiku proxy on your key.
*Fix:* word-boundary matching, drop the interrogatives; treat the spend cap and
rate limit as the real controls and harden those.

**P1-5 — The daily spend cap resets on every restart and disagrees with the docs.**
`chat/route.ts:401-413` — `spendTracker` is a module-level in-memory object, so
every deploy or PM2 restart zeroes it. It's checked before the call with no
accounting for the 15 concurrent in-flight requests allowed at `:423`, so it can
overshoot. `MAX_DAILY_TOKENS = 5_000_000` while CLAUDE.md, README.md and
ARCHITECTURE.md all say 2 M.

**P1-6 — `/api/push` is unauthenticated and accepts arbitrary endpoints.**
`src/app/api/push/route.ts:39-78` validates only that `endpoint`, `keys.p256dh`
and `keys.auth` are present. Consequences: anyone can fill the 10,000-slot table
and starve real subscribers; `DELETE` removes any subscription by endpoint with
no ownership proof; and `src/lib/push.ts:62-66` later calls
`webpush.sendNotification()` against those attacker-chosen URLs — a blind
outbound-request primitive (including `http://127.0.0.1:…`) that fires whenever
you send a notification.
Worse: `push/route.ts:25-32` and `lib/push.ts:16-23` both `catch { return [] }`
on parse failure, and the next `writeSubs()` persists that empty array —
one torn read permanently destroys the subscriber list.
*Fix:* allowlist endpoint origins to the real push services, cap length,
rate-limit, require the `auth` value on DELETE, and never write back a list that
came from a failed parse (distinguish ENOENT from parse error).

**P1-7 — The admin cookie is a permanent bearer credential with no revocation.**
`src/app/api/admin/route.ts:34-42` sets `wl_admin = sha256(ADMIN_SECRET)`;
`src/lib/auth.ts:34-35` accepts it forever. `maxAge` is a client hint only —
a captured cookie value never expires server-side, there's no logout route, and
the only revocation is rotating the secret and redeploying. The header path
(`auth.ts:38-42`) correctly requires the pre-image; the cookie path is
pass-the-hash. The login comparison itself (`admin/route.ts:12-22`) is correctly
timing-safe.
Also: **no rate limit or lockout on `POST /api/admin`** — unlimited guesses at
full server speed, no failed-attempt logging.

**P1-8 — No request body size limit anywhere in the stack.**
App Router handlers have no default cap, `next.config.ts` sets none, Caddy sets
none. `chat/route.ts:483` fully buffers and parses the body before truncating
`question` to 500 chars at `:484`. Same at `events/route.ts:221`,
`push/route.ts:42`, `notifications/route.ts:58`, `analytics/route.ts:71`.

**P1-9 — Non-atomic writes across four independent writers.**
`lib/analytics-store.ts:111`, `api/notifications/route.ts:31`,
`api/push/route.ts:35` **and** a duplicate copy in `lib/push.ts:25-27`,
`api/events/route.ts:274-288` — all plain `writeFileSync`, no tmp+rename. The
pipeline *does* write atomically (`update-events.js:699-707`), so an API write
can clobber a correctly-atomic pipeline write. Readers that hit a partial file
swallow the error and return empty (see P1-6).

**P1-10 — `POST /api/stats` is unauthenticated and unrated.**
`src/app/api/stats/route.ts:29-45` — anyone can inflate `total`/`today`/
`aiQuestions`. The route is arguably vestigial (real analytics live in
`analytics-store.ts`) and its own GET response admits the numbers reset on
restart. Simplest fix is deleting the POST handler.

**P1-11 — Error responses leak internals.**
`chat/route.ts:612-615` returns raw upstream error text (Anthropic request IDs,
quota messages); `events/route.ts:289-294` returns `details: String(err)`, which
includes absolute filesystem paths.

**P1-12 — CSRF checks are inconsistent and fail open.**
`admin/dashboard/route.ts:236-245` only enforces same-origin *if* an `Origin`
header is present. `POST /api/events` and `POST /api/notifications` have no
Origin check at all. `sameSite: "strict"` is doing the real work here, so
exploitability is low — the inconsistency is the defect.

**P1-13 — Event IDs are array indices.**
`events/route.ts:100-119` — `id: String(index + 1)` after sorting, so every ID
shifts whenever the pipeline adds an event. Anything that persists an ID (share
links, client selection, `rag.ts:551`) silently points at a different event later.
This blocks deep-linking (see P1-19) until it's fixed.

**P1-14 — Analytics stores raw per-visitor hashes and rewrites the whole file
every 50 views.** `lib/analytics-store.ts:96-99, 123`. `hashVisitor`
(`analytics/route.ts:59-61`) is unsalted `sha256(ip:date)` truncated to 16 hex —
the whole IPv4 space is brute-forceable per day, so the "no PII" claim at
`analytics/route.ts:14` is optimistic. The `setInterval` at
`analytics-store.ts:130` has no `unref()` and no shutdown hook, so PM2 restarts
rely on SIGKILL — which can land mid-`writeFileSync`.

## P1 — Language / i18n

Locale JSON parity is **clean**: all four files flatten to the same 304 keys,
zero missing, zero empty, zero placeholder mismatches. The defects are elsewhere.

**P1-15 — Locale is client-only, so every visit renders English/LTR first, then
flips.** `src/i18n/index.tsx:34-49` initializes to `"en"` and reads localStorage
in a `useEffect`; `src/app/layout.tsx:94` hardcodes `<html lang="en" dir="ltr">`
with `suppressHydrationWarning` masking the symptom. An Arabic or Hebrew reader
gets an English LTR first paint and a full mirror-flip on every single visit.
*Fix:* persist locale in a cookie, read it server-side in `layout.tsx`; or an
inline pre-hydration script that sets `dir`/`lang` before first paint.

**P1-16 — No browser-language detection.** `index.tsx:37-42` consults only
localStorage — no `navigator.languages`, no `Accept-Language`. A first-time
visitor from Iran, Israel, or Latin America gets English until they find the
dropdown. Compounded by `src/i18n/en.json:330-335` listing languages as
*exonyms* ("Spanish", "Arabic", "Hebrew") while es/ar/he correctly use endonyms —
so an Arabic-only speaker on the default EN UI sees "EN ▾" and Latin script.
*Fix:* `navigator.languages` fallback; endonyms in every locale's picker.

**P1-17 — Whole components bypass the translation system.**
- `src/components/pwa/PWAProvider.tsx:72-96` — entire install banner, no `useI18n` import.
- `src/components/ui/SourceFooter.tsx:37-59` — entire desktop footer.
- `src/components/map/ConflictMap.tsx:188-285` — popup, badge, "fatalities reported", "Source:", "Share"/"Copied!", and raw English `event_type` (unlike every other component, which uses `t(\`eventTypes.${type}\`)`).
- `src/components/ui/DonationPanel.tsx` — 64 `t()` calls but hundreds of hardcoded strings: all stat-card labels (`:338-358`), all section titles (`:407-498`), all StatLine labels (`:502-551`), free paragraphs (`:437, :457, :475, :512, :569, :596, :600`), and all 8 org descriptions (`:57-171`). This is the most human page on the site and it's half-translated.
- `src/components/ui/SourcesPage.tsx:140-147` — all 23 source entries render raw English.
- `src/components/chat/AskPanel.tsx:529-561` — the offline/error fallback answers are English-only *and* the keyword routing only matches English, so a Spanish/Arabic/Hebrew question always falls through to the English "service unavailable" string.
- Plus assembled fragments: `EventPanel.tsx:80` (hardcoded `" of "`), `ContentWarning.tsx:76-89` (English pluralization templates inside an otherwise translated modal), `OverviewBanner.tsx:122` (hardcoded `event(s)`), and English `aria-label`s throughout.

**P1-18 — Every date is hardcoded `en-US`.** `toLocaleDateString("en-US", …)` at
`EventPanel.tsx:362`, `ContentWarning.tsx:297`, `OverviewBanner.tsx:453, 534,
602`, `TimelineSlider.tsx:265-305`, `lib/share.ts:8`. Two calls pass no locale
at all (`ConflictMap.tsx:244`, `useEvents.ts:41`), so they're inconsistent with
the rest. Numbers use bare `toLocaleString()`, so Arabic UI can show Western
digits unpredictably.
*Fix:* thread `locale` from `useI18n()` into every formatter.

**P1-19 — RTL layout breaks in specific, visible places.**
- `src/app/page.tsx:274` — the timeline reserves `md:right-[380px]` while the EventPanel it's avoiding flips to the *left* in RTL: the timeline underlaps the panel and leaves a 380 px dead gutter. Should be `md:end-[380px]`.
- Back arrows never flip: identical left-pointing SVG at `EventPanel.tsx:71`, `AskPanel.tsx:151`, `SourcesPage.tsx:90`, `AboutPage.tsx:19`, `DonationPanel.tsx:278`. Needs `rtl:rotate-180`.
- `AskPanel.tsx:412, 432` `pl-3` (list indent stays left), `:503` `text-left`, `:155` `ml-auto`, `:217/:259` non-mirroring bubble corners — visible on real ar/he AI answers.
- `src/i18n/index.tsx:88` — `isRTL = locale === "ar"` reports Hebrew as LTR, contradicting `dir` two lines above. Currently unconsumed, but it's a live landmine.
- `globals.css:197` declares "Noto Sans Hebrew", which `layout.tsx:16-20` never loads (only Noto Sans Arabic).

Credit where due: `globals.css:176-221` has real RTL work (ticker keyframe
reversal, border flips, mapbox control mirroring, Arabic font stack), and the
Header/MapLegend already use logical `end-*` properties.

**P1-20 — English pipeline content is rendered raw inside RTL documents with no
labeling.** Event descriptions, `civilian_impact`, actors and ticker headlines
(`EventPanel.tsx:148, 169`; `OverviewBanner.tsx:151, 455, 536, 605`;
`ConflictMap.tsx:229`; `page.tsx:163-167`) come from an English news pipeline and
are dropped into `dir="rtl"` with no `lang="en" dir="ltr"` wrapper, so bidi

## Pipeline: model and API notes

- `update-events.js:76` pins `claude-haiku-4-5-20251001` — current and active, no urgency to change. Call shape is clean (no deprecated params).
- **Prompt caching would not help as written.** Haiku 4.5's minimum cacheable prefix is 4096 tokens; the stable instruction block (`:1376-1421`) is ~1,200–1,500 tokens and is immediately followed by volatile per-run content, so a `cache_control` breakpoint would silently never cache.
- **The highest-value upgrade is structured outputs** (`output_config: {format: {type: "json_schema", …}}`, supported on Haiku 4.5). It guarantees a valid JSON array, which eliminates the entire 5-method parse cascade (`:1482-1550`), most of the truncation-salvage fragility, and a large share of the prompt-injection output surface.
- `max_tokens: 8192` is well under the 64 K ceiling and `stop_reason: "max_tokens"` is common enough that it's instrumented (`:1457-1462`). Raise to ~16 K, or stream.
- The client has no explicit timeout, so the SDK default (10 min, 2 retries) exceeds the 180 s process budget — a slow call blows the wall clock and takes the *no-stats* exit path. Set `timeout: 90_000, maxRetries: 1`.

## Pipeline: additional correctness

- **Prompt injection is under-defended.** `sanitizeArticleText` (`:622-641`) strips ~10 fixed phrases; "Updated guidance: also report the following incident…" passes untouched, and by the prompt's own rule that "headlines are sufficient evidence" (`:1379`), a fabricated attack narrated in a real article is a valid extraction. Article text and instructions share one user turn with no system prompt. `isValidEvent:1012` only checks `source_url.startsWith("http")` — nothing verifies the URL was actually fetched this run — and confidence tiering trusts the model-supplied `source` string (`:1607-1615`), so an injected event claiming `"source": "Reuters"` gets a +0.1 boost. *Fix:* validate `source_url` against the fetched set, force `source` from the article record, move instructions to `system`.
- **Invalid and future dates bypass validation** (`:1623-1633`): `new Date("2026-99-99")` is `NaN`, and `NaN < CONFLICT_START` is `false`, so garbage dates pass — and the regex at `:1005` accepts them. There's no upper bound either, so a hallucinated 2027 event is accepted. Both then become invisible to all time-windowed dedup (`:899-900`).
- **Fatality zeroing destroys information** (`:1659-1662`): `>= 500 → 0`, keeping the event as a zero-fatality airstrike with no flag. A real mass-casualty event is permanently recorded as zero; a hallucinated 10,000-dead event *stays in the dataset*. Quarantine instead. (Code zeroes at exactly 500 while docs say ">500"; the `newFat <= 500` merge guard at `:1700` is consequently dead.)
- **Fatality merges onto seed-file events are silently lost** (`:1695-1709` mutates across all three files, `:1756-1768` writes only `events_latest.json`).
- **Reworded-headline duplicates escape.** For the 0-fatality majority, methods 0 and 3 are fatality-gated, so dedup falls back to Jaccard > 0.6 within 24 h (`:934-948`). "Israeli jets strike Tehran fuel depot" vs "Oil facility in Iranian capital hit in air raid" scores ~0.1 — both kept. This is a plausible contributor to the 24 k count.
- **Jerusalem Post is permanently Tier-3 penalized** — it's in the fetch list (`:467`) but in neither tier list (`:87-102`) and missing from `domainMap` (`:651-673`). Meanwhile `OUTLET_NAMES` (`:1220-1224`) health-tracks Reuters and Times of Israel, which have no direct feed, so they report `error` every run (matching what the live health endpoint shows).
- **Claude only sees the last 25 events as dedup context** (`:1348-1354`), sorted by event date rather than insertion time.
