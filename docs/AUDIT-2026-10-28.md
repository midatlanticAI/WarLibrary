# War Library audit — 2026-10-28

**Scope:** why the site has become slow to open, what has aged, and whether the
Cloudflare move in `docs/CLOUDFLARE-MIGRATION.md` still makes sense against
today's numbers. Every figure below was measured on this date against
https://warlibrary.midatlantic.ai or against `master` @ `de72e13` on this
machine. Nothing was changed on the server.

---

## 1. The headline: production is running the April build

The droplet's Node process reports **203 days of uptime** (`/api/health`
`uptime_seconds: 17595933`), which puts its start around 2026-04-08. The last
commit on `master` before PR #1 is `db7f403` (2026-04-06). Everything merged on
2026-07-27 in PR #1 — the cached events API, ETag/304 polling, map clustering,
feed virtualisation, structured-output extraction, the strict date guard, admin
hardening — **has never been deployed.**

Verified directly against the live API rather than inferred from uptime:

| Request | Expected on `master` | Live response |
|---|---|---|
| `/api/events?summary=1` | ~50 KB aggregate | 6,845,157 bytes, full dataset |
| `/api/events?fields=lite` | ~1/4 of full | 6,845,157 bytes, full dataset |
| `/api/events?limit=5` | 5 events | 6,845,157 bytes, full dataset |
| `ETag` header on `/api/events` | weak ETag | **absent** |

The query parameters are silently ignored and there is no ETag, which is
exactly the pre-PR route (`git show db7f403:src/app/api/events/route.ts`).

### What the April build does to every visitor

Reading the deployed code, not the current one:

1. **Server, per request:** `GET /api/events` reads and `JSON.parse`s all three
   data files, deduplicates, sorts with two `new Date()` per comparison, and
   serialises the result. No module cache. The serialised body is **29.2 MB**
   (`original size modulo 2^32 29175731` from the gzip header), **6.8 MB on
   the wire**. Measured time to first byte: **1.8–2.6 s**, and `/api/health`
   alone takes **0.8–1.3 s** because it also parses the 29 MB file to count
   rows. This is single-threaded Node, so concurrent visitors queue behind one
   another's parses.
2. **Client, on load:** the browser downloads 6.8 MB, decodes 29 MB of JSON,
   and the pre-PR `ConflictMap` renders **one React `<Marker>` per event** —
   37,507 DOM nodes on a map — while `EventPanel` renders the full list with no
   virtualisation.
3. **Client, every 60 seconds:** the pre-PR `useEvents` polls with
   `cache: "no-store"` and no `If-None-Match`, so each open tab re-downloads
   the full 6.8 MB and re-parses it every minute, forever.

In July the dataset was 24,638 events and the July audit measured ~0.4 s of
server compute. It is now **37,507 events (+52%)**, growing ~4,300 a month,
and the deployed code has a cost that scales linearly with that. "Slow to get
into" is the predictable result, and it will keep getting worse by ~12% a
month until the build on the server changes.

### The fix is already written

`master` as it stands answers all three problems: module-scope dataset cache
keyed on file mtimes (one parse per pipeline write instead of per request),
weak ETag so the 60 s poll is a 304 with no body, `fields=lite` /
`summary=1` / `from`,`to` / `limit`,`offset` on the API, GPU-side clustering on
the map, and a virtualised feed. Locally on this tree: `tsc --noEmit` clean,
**271/271 unit tests pass**.

One residual on `master` worth fixing before or just after deploy: the current
`useEvents.ts` still requests bare `/api/events` — the full 29 MB payload — even
though the route now supports `fields=lite`. The map and feed need the lite
fields; the narrative fields can be fetched per event on open. That alone cuts
the first load by roughly 4×, and it is a one-line change on the client plus a
small detail fetch. See §5.

## 4. Cloudflare: does it still make sense?

Short answer: **yes, and more than in July**, for two reasons that were not
true then. Re-read against the Cloudflare docs today, with the dataset at
37,507 events / 29.2 MB serialised.

### What changed in our favour

1. **The script-size blocker is gone.** The July doc rejected shipping `jsdom`
   (12 MB) against a "10 MB gzipped" Worker limit. The Workers limits page now
   states **"Worker size (uncompressed): 64 MiB"** on both Free and Paid, and
   "There is no compressed size limit." So `@mozilla/readability` + `jsdom` can
   ship as-is; the `HTMLRewriter` rewrite in §6 of the July doc is no longer
   required. (The OpenNext adapter page still quotes 3 MiB / 10 MiB; treat the
   Workers limits page as authoritative and verify with a `wrangler deploy
   --dry-run` of the pipeline bundle before relying on it.)
2. **OpenNext supports "all minor and patch versions of Next.js 16"** on the
   Node runtime, with ISR and route handlers. The app shell ports without a
   framework change. Node Middleware is unsupported; this project has none.

### What changed against us

1. **The in-isolate JSON approach is now further out of reach.** July measured
   60.5 MB peak heap to parse a 19.6 MB file. The file is now 29.2 MB
   serialised, so the same approach lands around **90 MB peak against a 128 MB
   isolate** that is shared across concurrent requests. D1 is not an option
   among several; it is the only read path that works.
2. **Cron CPU budget is 30 s** for a trigger firing more often than hourly
   (15 min only at ≥1 h). The pipeline's last run took 24.5 s wall-clock,
   nearly all of it waiting on Anthropic and RSS, so CPU is well under — but on
   Workers it must not `JSON.stringify` a 29 MB file every run. Inserting into
   D1 instead of rewriting the file removes that cost entirely, and is the
   point.

### Limits re-verified today

| Limit | Value (Paid) | Our need |
|---|---|---|
| Memory per isolate | 128 MB | Fine with D1; fatal with the JSON file |
| Worker size | 64 MiB uncompressed | jsdom 12 MB fits |
| CPU per HTTP request | 30 s default, 5 min max | ms |
| CPU per cron (< 1 h interval) | 30 s | ~1–2 s if D1-backed |
| Cron wall-clock | 15 min | 25 s today |
| Subrequests | 10,000 | ~600 (589 articles fetched last run) |
| D1 database size | 10 GB | 29 MB (0.3%) |
| D1 queries per invocation | 1,000 | Batch inserts: tens |
| D1 bound params per query | 100 | 17 columns → ≤5 rows per statement, so use `db.batch()` |

### Infrastructure already in place

- The domain is already proxied through Cloudflare (`server: cloudflare`,
  `cf-cache-status: DYNAMIC` on every response).
- `wrangler` 4.154 is installed and **authenticated to the Mid-Atlantic AI
  account** on this machine, so D1/KV/R2 creation needs no new setup.

### The four decisions from July, with recommendations

1. **Admin controls** — reframe. "Trigger a run" becomes a protected route that
   fires the cron handler; "restart PM2" and "edit crontab" go away because
   there is nothing to restart or edit. The read-only dashboard survives intact.
2. **Impossible dates** — there are now 13, plus 4 future-dated. Import them
   into a `events_quarantine` table with a `reason` column rather than
   dropping them, so the D1 `CHECK` constraints can stay strict and nothing is
   deleted. John reviews the quarantine table at leisure.
3. **Hybrid or full** — go full. With jsdom shippable, the pipeline has no
   remaining hard blocker, and the droplet costs money to parse JSON.
4. **`country_code` backfill** — schema allows NULL; do it after cutover as a
   query, not before as a blocker.

### Recommended build order

`docs/CLOUDFLARE-MIGRATION.md` §8 phases still hold, with §6 simplified:

- **Phase 0** D1 schema + import of the live 37,507 rows (export from the
  droplet, `wrangler d1 execute --file`), `scripts/validate-pipeline.js`
  pointed at D1, same pass count as today. Audit the 11 `writeFileSync` sites.
- **Phase 1** Worker serving `/api/events`, `/api/stats`, `/api/health` from
  D1 at a staging hostname; diff responses against the droplet.
- **Phase 2** DNS cutover of the public site via OpenNext. Latency win lands.
- **Phase 3** Pipeline as a Cron Trigger + Queue consumer, jsdom intact.
- **Phase 4/5** Admin reframe, retire droplet.

## 5. Recommended sequence

John's stated order is: assess Cloudflare → build it if it makes sense →
then release the DO version. The assessment says build it. On ordering, one
observation to weigh: **deploying `master` to the droplet is a single
`deploy.sh` run and fixes the slowness on its own** (cache, 304 polls,
clustered map, virtualised feed), while the Cloudflare build is weeks. Every
day in between, every visitor pays the April tax described in §1. If the
droplet release goes first, the Cloudflare build also starts from a pipeline
that is already proven on the real API, including the Opus 4.8 advisor that has
never hit the endpoint (kill switch: `ADVISOR_ENABLED=false`).

Either way, the work list:

**A. Droplet release (whenever it runs)**
1. Commit the `JsonLd.tsx` change.
2. `npm audit fix` + the minor bumps in §3; re-run the gate.
3. Change `useEvents.ts` to request `fields=lite`, add a per-event detail fetch
   for `civilian_impact`/`actors` on open; make `/api/stats` and `/api/health`
   read the cached dataset's count.
4. Delete the Mapbox CDN stylesheet link in `layout.tsx`.
5. Set `ADVISOR_ENABLED=false` for the first production runs, read
   `pipeline-stats.json` for a day, then decide.
6. `DEPLOY_SERVER=root@<droplet-ip> bash deploy.sh`. The droplet IP is not
   recorded anywhere in the repo or memory; John supplies it.
7. On the droplet, after deploy: run `scripts/audit-data.js` (annotate only)
   and bring the 13 + 4 date problems to John before anything moves.

**B. Cloudflare build** — §4 order. Phase 0 can start today on this machine
with the authenticated `wrangler`; it needs the live `events_latest.json`
exported from the droplet first.

**C. Cheap interim, no deploy needed:** a Cloudflare Cache Rule that caches
`/api/events` at the edge for 60 s would turn the 2 s server parse into a hit
for everyone after the first visitor per minute. It does not fix the 6.8 MB
download or the 37k markers, but it takes the droplet out of the critical path
immediately. Dashboard change, reversible, John's call.
